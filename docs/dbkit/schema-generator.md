# Schema SQL generator

Status: implemented for `user-service` and `invoice-service`. `email-service`
still hand-writes its SQL and declares `SchemaSource::Handwritten`.

Each service keeps a `SCHEMA` static in `src/db/schema.rs`. The `Schema` value
carries its SQL, its models, its schema dependencies and whether the SQL is
generated or hand-written:

```rust
pub static SCHEMA: Schema = Schema {
    name: "invoice",
    sql: include_str!("../db/schema.sql"),
    models: &MODELS,
    dependencies: &[&user_service::db::schema::SCHEMA],
    source: SchemaSource::Generated,
};
```

## Opt-in

Generation is per service:

- `SchemaSource::Generated` promises that `sql` equals `Schema::generate()`.
  The service adds a generator binary and a drift test.
- `SchemaSource::Handwritten` leaves the file alone. Calling `generate()` on it
  returns a problem instead of producing SQL.

`email-service` is the hand-written example. It has no generator binary and no
drift test.

## Generated files

Generated files are normal SQL files, checked in and not ignored by git. The
first line identifies them:

```sql
-- Generated by dbkit from the "invoice" schema. Requires: user. Do not edit.
```

A service with no dependencies gets the shorter form:

```sql
-- Generated by dbkit from the "user" schema. Do not edit.
```

The header is followed by a blank line and the DDL.

## What the generator reads

- Tables and columns in declaration order, including flattened columns.
- Column types, nullability, defaults and virtual generated expressions.
- Primary keys and unique keys.
- Non-unique indexes from `#[db(index(columns = [...], name = "..."))]`.
- Foreign keys, including `on delete` and `on update` actions.
- Trigger declarations and full definitions: target table, timing, events,
  level, condition, function, language and body.

The generator needs no database connection. `Schema::generate()` uses the
service's own models as the tables to emit and `all_models()` as the known
tables for cross-table foreign keys. This is what lets an invoice fragment
reference `tenant` without emitting `create table "tenant"`.

## API

In `dbkit::schema`:

```rust
impl Schema {
    /// Renders this service's tables, keys, indexes and triggers from its models.
    pub fn generate(&self) -> Result<String, Vec<String>>;

    /// Applies dependency fragments and this fragment, dependencies first.
    pub async fn apply(&self, pool: &PgPool) -> sqlx::Result<()>;

    /// Checks the live schema against this fragment and its dependencies.
    pub async fn check(&self, connection: &mut PgConnection) -> sqlx::Result<Vec<String>>;

    pub fn all_sql(&self) -> String;
    pub fn all_models(&self) -> Vec<TableMeta>;
}

/// Renders the owned tables, using known to validate cross-table targets.
pub fn generate(owned: &[TableMeta], known: &[TableMeta]) -> Result<String, Vec<String>>;
```

`all_sql` and `all_models` walk dependencies depth-first and include each
service once, so a diamond such as `C -> A, B` and `A -> B` applies `B` once.

## Output order

1. Tables, with columns, primary keys and unique constraints inline.
2. Foreign keys as `alter table ... add constraint ...`.
3. Non-unique indexes.
4. Trigger functions, deduplicated by name and sorted by name.
5. Triggers, sorted by table and name.

Foreign keys are added after every table, so service order and foreign-key
cycles do not affect the generated fragment. The generator does not emit
`begin`, `commit`, `if not exists` or drops; it targets a fresh database.

## Names

- Primary key: `<table>_pkey`.
- Unique key: `<table>_<columns>_key`.
- Foreign key: `<table>_<columns>_fkey`.
- Index: the annotation's `name`, or `<table>_<columns>_idx`.
- Function and trigger names come from the annotations.

Every identifier is quoted and embedded quotes are doubled. An identifier over
63 bytes is reported as a problem instead of being silently truncated.

## Trigger details

- Events are emitted in canonical order: insert, update, delete, truncate.
- `level` decides `for each row` or `for each statement`.
- A condition becomes `when (<condition>)`.
- A function body is emitted between dollar-quote tags. `$$` is used first;
  if the body contains it, the generator tries `$dbkit$`, `$dbkit_1$`, and so
  on.
- A trigger definition must be installed on a table the service owns.
- Two triggers on different tables default to the same function name. The
  generator reports the collision and the annotation must set
  `function = "..."`.

## Errors

`generate()` returns one message per problem:

- A table name declared more than once.
- A foreign-key target outside the known models.
- A trigger installed on a table the service does not own.
- A trigger declaration with no definition.
- Conflicting trigger definitions for one `(table, name)`.
- Conflicting bodies or languages under one function name.
- An identifier over 63 bytes.
- Calling `generate()` on a hand-written schema.

## Regenerating

```bash
cargo run -p user-service --bin user-schema > crates/user-service/src/db/schema.sql
cargo run -p invoice-service --bin invoice-schema > crates/invoice-service/src/db/schema.sql
```

Each generated service has a drift test:

```rust
#[test]
fn schema_sql_is_generated() {
    assert_eq!(
        SCHEMA.generate().unwrap(),
        SCHEMA.sql,
        "regenerate with `cargo run -p invoice-service --bin invoice-schema`"
    );
}
```

The live schema test still applies `SCHEMA` and runs `SCHEMA.check`, so a
generated file that omits an object fails there too.

## Cross-service composition

The deployment is one database with one PostgreSQL schema. Services are Rust
crates that own models, not separate database schemas. `Schema` composition
handles the shorter-term fragments:

- `SCHEMA.apply` applies dependency SQL first.
- `SCHEMA.check` checks the combined model list.
- A cross-service foreign key is a normal `foreign_key` annotation; no
  `external` marker is needed.

A future backend crate can build one combined `MODELS` list and generate one
complete schema. Until then, each generated service file is a fragment and is
applied through its `Schema`.

## Limitations

The generator does not create:

- Check or exclusion constraints.
- Deferrable constraints.
- Partial, expression, covering or concurrent indexes.
- Stored generated columns; `pg_virtual` is virtual only.
- Domains, enums, composite types, extensions, sequences, views or
  non-trigger functions.
- Grants, row-level security, policies, comments, collations, partitioning or
  table storage parameters.

A column default or generated expression may reference a function, domain or
extension that the generated file does not create. Those must exist before the
schema is applied. The generated file is not a migration.

## Adding another service

1. Add `src/db/schema.rs` with a `SCHEMA` static and `source:
   SchemaSource::Generated`.
2. Add `src/bin/<service>-schema.rs` that calls `SCHEMA.generate()`.
3. Generate the SQL file.
4. Add the drift test to the service's `tests/schema.rs`.
5. If the service references another service's tables, list that `SCHEMA` in
   `dependencies` and add the cross-service `foreign_key` annotations.
